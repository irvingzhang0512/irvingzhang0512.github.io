Agent多人共用为何会失控？来自Ankole的Business Agent架构设计分享

机器之心发布 Ankole 团队对开源 Business Agent 系统架构设计的分享，指出 Personal Agent 进入多人组织场景会因认知分叉、上下文泄密、状态分裂、轮询误差复利四类问题失控，并提出 Business Harness 的四项设计哲学。

📡 机器之心 · 2026-11-18 13:00

要点

  • 明确 Coding Agent（单次任务）、Personal Agent（个人跨会话）、Business Agent（组织级多角色多 Agent 协同）三类形态差异，并给出组织场景下四人机协同 Loop 失效模式，其中「99% 单次准确率 × 每天 288 轮轮询 → 全天至少错一次概率 ≈94.5%」的误差复利推算是很好的量化直觉。
  • 快慢路径分离：常规高频流转交给模型自己写的脚本执行，模型零消耗休眠，仅在规则外新情况、指标越界或业务规则变更（Harness-RSI 改写脚本）时被事件唤醒，把 Token 与随机性挡在日常执行器之外。
  • 动态权限与组织记忆：每次唤醒前取「Agent × 提问者 × 全体在场成员」的权限交集；引入负责人审核签名的固定写入通道与独立授权的职能 Agent 做隔离协查；组织记忆做成「共享关系目录 + 实时校验源文档权限」的多视角投影，区分客观事实与带署名的主观判断并持续校准提出者准确率。
  • 用 Actor 模型替代 Agentic Loop + Checkpointer 快照：每个会话/专职 Agent 是带私有状态与收件箱的驻留单元，天然处理并发插话与改口，防 Agent 互触发死循环；配合分层监督（代码执行剥离到无长期密钥的沙箱）+ 持久化动作账本（不可逆操作前记录、恢复后核对回执）解决长程容错与重复执行。

📡 美团技术团队

要点

  • 起点是 Karpathy 的 AutoResearch 极简原型（program.md 定规则、train.py 为 Agent 唯一可改的训练代码、prepare.py 冻结评估防“篡改裁判”+Git keep/reset 棘轮），迁移到企业云端后暴露 Prompt 声明不可信、异步环境差异、单线程 LOOP 只能维护一条时间线三大问题。

《Agent评测白皮书》系列02：商家 AI 助手的评测与优化闭环实践

美团技术团队以商家广告助手的投放巡检任务为案例，讲解了如何从业务 SOP 和真实 Bad Case 出发构建 Agent Benchmark，再用评测器校准、错误分析与回归选型，形成评测、优化的完整流程。

📡 美团技术团队

要点

  • 评测场景采用两条互补路径：从业务 SOP 自顶向下拆解成状态图，明确业务状态、数据依赖、条件分支、提前停止点、能力边界和跨 Skill 转交点，确保核心流程不遗漏；再从线上和离线 Bad Case 自底向上补齐边界与回归场景。KA 每日巡检最终形成 6 类、41 个场景。
  • 成功标准拆成三部分：执行流程是否遵循 SOP（工具调用顺序、必要步骤、并行效率、分支逻辑）；过程与结论是否有据可依（参数与任务语义一致、工具选择正确、输出忠实于工具返回）；交付物是否可交付（完整性、模板、结论表述）。这些标准再写成 Rubric，区分「成功必需项」和「仅用于质量分层诊断的指标」。
  • 判定机制按可取证程度分工：能从 Trace 中精确取证的检查项交给确定性 Grader，需要业务语义理解与证据关系的交给 LLM Grader，再通过评测器校准保证判定稳定可信。
  • 整体目标归纳为「可测、可信、可优化」：公开 Benchmark 只能借鉴其任务组织、环境构造和判定方法，不能直接当作上线依据，必须围绕自身业务建立 Task 集，并借助图灵平台持续回归与模型选型。

800 个 MCP Server、5000 个工具，AI 智能体的“微服务危机”来了

MCP Server 与工具数量爆炸式增长（800 个 Server、5000 个工具），正在让 AI 智能体面临类似“微服务爆炸”后的发现、治理与选型难题。

📡 InfoQ 中文 · ✍️ 作者：Leela Kumili · 2026-11-18 22:00

要点

  • 生态现状：MCP Server 已达 800 个量级、可调用工具超过 5000 个，Agent 可接入的工具池急速膨胀，但缺乏统一的发现与质量评估机制。
  • 核心矛盾：工具太多导致 Agent 在工具选择、上下文占用、权限边界、版本兼容上出现“微服务危机”式问题——注册中心、治理、可观测性等基础设施缺失。
